# CineRank 前端重构方案 —— 从"统计仪表盘"到"数据本体叙事"

> 目标读者：本项目的前端/后端开发者。
> 目标：把现有"六个场景共用一套通用模板（KPI + 条形榜 + 饼图 + 折线）"的统计式界面，
> 重构为**每个场景展现其数据本体特征**的领域界面——电影有海报、骑行有地图、
> 航班有延误榜与航线、基因有基因组轨道。
>
> 本方案中的外部数据源覆盖率、接口形态、字段可用性**均已实测验证**（见各节
> "可行性实测"），实测日期 2026-09-29，方法为真实 HTTP 请求与真实数据文件解析。

## 一、现状诊断

### 1.1 现有前端

| 项 | 现状 |
|---|---|
| 文件 | `app/frontend/index.html`（单文件，1018 行，含全部 CSS/JS） |
| 图表库 | `app/frontend/echarts.min.js`（ECharts **5.4.4 完整发行版**，1.0MB） |
| 页面 | 算法实验室 / 性能基准 / 应用 / 六场景总览 / 关于 |
| 场景切换 | `#scn-sel` 下拉 → `scnSwitch()`；movie 走 `#app-movie`，其余五场景走通用 `#app-generic` |
| 通用模板 | KPI 四连 + 横向条形榜（`g-ch`）+ 名称检索卡片 + 分类饼图 + 年份折线 |

**ECharts 能力实测**（用 Node SSR 对本仓库的 `echarts.min.js` 逐类型渲染验证）：

| 图表/组件 | 可用性 | 验证方式 |
|---|---|---|
| `map` series + `registerMap` | ✅ | SSR 渲染成功 |
| `geo` 组件 + `scatter`/`effectScatter` 叠加 | ✅ | SSR 渲染成功 |
| `lines` series（`coordinateSystem:'geo'`） | ✅ | SSR 渲染成功 |
| `graph` series（力导向 / 环形） | ✅ | SSR 渲染成功 |
| `treemap` / `sunburst` / `themeRiver` / `graphic` / `custom` / `pictorialBar` / `boxplot` / `parallel` / `gauge` / `funnel` / `radar` / `calendar` / `heatmap` | ✅ 模块均已注册 | 包内字符串注册表逐项确认（`series.<type>` 各 1 处注册） |

> 结论：**不需要更换图表库**，现有 ECharts 完整版已包含地图、图、流线、日历热力等全部所需能力。
> 这是本次重构最大的有利条件。

### 1.2 核心问题

1. **六个场景长得一样**：movie 之外的五个场景全部走同一个 `#app-generic` 模板，
   只有标签文字由 `meta.json` 驱动。电商 476,002 个商品、航班 356 个机场、
   网页图 875,713 个节点，在界面上都是"一根横向条 + 一个名字"。
2. **丢掉了数据里最有信息量的字段**：
   - 骑行原始 CSV 里**有起终点经纬度**，`pre_bike.py` 只取了站点名与分钟，坐标被丢弃（第 80~98 行）；
   - 电影只有"主类型"一个标签（`preprocess.py:90` 的 `genres.split("|")[0]`），多类型信息被丢弃；
   - 航班的**航司**只存在于 `ledger.dat` 的键里，`entities.dat` 只有机场，界面上看不到航司维度；
   - `records.jsonl.gz` 里有起终点对（`{"s":…,"e":…}`）、日期、距离等，全部未进入 UI。
3. **没有领域物件**：电影没有海报，商品没有商品图，机场没有地理位置，
   基因没有基因注释——用户看到的是"编号 + 数字"。
4. **故事线缺失**：题目要求论证"排序是许多领域的关键子问题"，
   但界面没有讲出"城市早晚高峰调度"、"供应链备货"、"航司准点考核"这些真实问题。

## 二、P0 数据保真性修复（先做，否则一切可视化都是错的）

在重构 UI 之前，必须修掉两处**用户可见的数值错误**——它们会让"更真实地展现数据"这一目标直接落空。

### 2.1 电影均分系统性偏低 0.25 星（必修）

- 键编码：`preprocess.py:55` → `ridx = int(rating * 2) - 1`，即 `rating = (ridx + 1) / 2`。
- 显示公式：`app/ml_index.h:66` → `return count ? (sumIdx / (double)count + 0.5) / 2.0 : 0.0;`
  即 `mean = avgIdx/2 + 0.25`，正确应为 `avgIdx/2 + 0.5`。
- 实测（来自随包 `postings_1e6.dat`）：

  | 影片 | 评分条数 | 平均 ridx | 当前 UI 显示 | 正确值 | 误差 |
  |---|---|---|---|---|---|
  | Shawshank Redemption, The (1994) | 3292 | 7.838 | 4.169 | **4.419** | −0.250 |
  | Forrest Gump (1994) | 3284 | 7.052 | 3.776 | **4.026** | −0.250 |
  | Pulp Fiction (1994) | 3150 | 7.383 | 3.941 | **4.191** | −0.250 |

- 修复：`ml_index.h` 的 `MovieRow::mean()` 改为
  `return count ? (sumIdx / (double)count + 1.0) / 2.0 : 0.0;`

> 注意：还有一处**数据口径不一致**需一并确认——`preprocess.py` 是 10 档 `ridx∈[0,9]`
> （`rating*2-1`），而 `app/pre/pre_amazon.py` 是 9 档 `ridx∈[0,8]`（`stars*2-2`）。
> 两个场景的 `meanScale/meanOffset` 必须各自匹配自己的编码，见下条。

### 2.2 电商星级系统性偏低 0.5 星（必修）

- 键编码：`pre_amazon.py:49` → `ridx = int(stars * 2) - 2`，即 `stars = ridx/2 + 1.0`。
- 显式换算：`app/data/amazon/meta.txt` → `meanScale=0.5`、`meanOffset=0.5`
  → `mean = 0.5*avgIdx + 0.5`，正确应为 `0.5*avgIdx + 1.0`。
- 实测（来自随包 `amazon/postings_1e6.dat`）：

  | 商品 ASIN | 评论数 | 平均 ridx | 当前 UI 显示 | 正确值 | 误差 |
  |---|---|---|---|---|---|
  | B0074BW614 | 2332 | 7.391 | 4.196★ | **4.696★** | −0.500 |
  | B00DR0PDNE | 2103 | 7.437 | 4.218★ | **4.718★** | −0.500 |
  | B007WTAJTO | 1811 | 7.494 | 4.247★ | **4.747★** | −0.500 |

- 修复：`pre_amazon.py` 的 `meanOffset` 改为 `1.0`，并重跑预处理重写
  `app/data/amazon/meta.txt` 与 `meta.json`（`EntityStore::load` 只读这两个文件，无需改代码）。

### 2.3 航班"平均延误"目前是档位号，不是分钟（建议修）

`pre_flight.py:55` 把 `DepDelay` 压成 0~9 档，`entities.dat` 只累计**档位号之和**，
因此界面上 `mean` 显示的"平均延误"实际是"平均延误档"（0~9 的无量纲数），
而不是乘客能理解的"平均延误 23 分钟"。

- 修复：`pre_flight.py` 在聚合时**额外累计真实 `DepDelay` 分钟和**（新增一列或复用 `entities.dat` 的 `val` 字段），
  使 UI 可显示 `平均延误 XX.X 分钟`；档位号保留用于计数排序叙事。
- 同时建议输出 `准点率 = P(delayIdx ≤ 2)`（≤15 分钟，业界常用口径），供 E 场景的"准点率分组"使用。

### 2.4 其余口径澄清（写进 UI 文案，避免"造假"观感）

| 项 | 现状 | UI 应如何呈现 |
|---|---|---|
| 航班只有 4 个月 | `stats.txt`：实际取得 1、10、11、12 月，2–9 月直链不可达 | 月度趋势图**必须标注缺月**，不要画成连续 12 个月 |
| 骑行只有 9 个月 | `stats.txt`：S3 年度 zip 实际含 1–9 月分片 | 同上，月份轴标注实际覆盖范围 |
| 基因声称 23 轮，实际 12 轮 | `gene_stats.json` 实际 12 轮，`k` 最大 2048 时 `distinct=4,641,653`（含哨兵已全区分）→ **提前终止** | 文案写"实际 12 轮（全后缀已区分，提前终止；理论上界 23 轮）" |
| README 称"策略随轮次变化" | `gene/rounds.csv` 12 轮**全部**是 `S5 基数排序+S5 基数排序` | UI 如实显示每轮策略；不要预设"会变化"的叙事 |
| 网页图无节点名 | web-Google 只有整数 id，无主机名/URL，且不存在官方 编号→网址 对照 | 措辞用「网页 #数据集原始编号」（不用冷感的 Node）；页首 caveat + 榜单卡 note 显著说明"数据集不含 URL、无对照表，无法标网址也不编造"，图形 tooltip 内再提示一次 |
| 骑行站点热度是"出发量" | `postings.dat` 键用的是 `start station id` | 文案写"出发量"，或补采 OD 后区分"出发/到达" |

## 三、总体架构：场景化组件框架

### 3.1 设计原则

1. **一个场景 = 一个"故事板"（story board）**，由若干"面板（panel）"组成；
   面板类型共享，场景配置声明。
2. **配置驱动**：新增场景只需在 `SCENES` 注册表加一个对象（沿用现有"零改动扩展"卖点）。
3. **数据驱动降级**：每个面板声明自己依赖的数据文件/接口；数据缺失时渲染
   "该面板需要运行 `xxx` 生成"的占位卡，而不是空白或报错。

### 3.2 文件结构（建议）

当前服务器只硬编码了 `/index.html` 与 `/echarts.min.js` 两条静态路由
（`app/server.cpp:1056-1061`）。为承载海报、GeoJSON 与拆分后的 JS，需要先加一条
**白名单静态路由**（详见[第十一节](#十一后端新增接口与静态资源路由)）：

```
app/frontend/
├── index.html            # 骨架 + 场景容器（不再内联全部逻辑）
├── echarts.min.js        # 不变
├── app/
│   ├── core.js           # 场景注册表 / 面板渲染器 / 通用组件（KPI、榜单、检索、骨架屏）
│   ├── scn_movie.js      # 场景 A 面板
│   ├── scn_amazon.js     # 场景 B
│   ├── scn_bike.js       # 场景 C
│   ├── scn_web.js        # 场景 D
│   ├── scn_flight.js     # 场景 E
│   └── scn_gene.js       # 场景 F
├── assets/
│   ├── posters/          # 电影海报（本地化，离线可用）
│   ├── products/         # 电商商品缩略图（本地化）
│   ├── geo/              # nyc.json / us-states.json / world.json
│   └── maps.meta.json    # 资产清单（key → 文件名 / 缺失标记）
└── data-enrich/          # 增强数据（由 enrichment 脚本生成）
    ├── movie_meta.json   # movieId → {poster, imdbId, genres[], mean, hist[10]}
    ├── amazon_meta.json  # itemDense → {title, price, img, cats[], hist[9]}
    ├── bike_stations.json# stationId → {lat, lon, name, borough}
    ├── bike_od.json      # 站点对流量 Top-N
    ├── bike_hourweek.json# 24×7 骑行量矩阵
    ├── flight_geo.json   # IATA → {lat, lon, name, city}
    ├── flight_routes.json# Top-N 航线 + 延误/准点率
    ├── flight_group.json # 航司/机场/月 的准点率与平均延误（多级键榜单数据）
    ├── gene_genes.json   # GFF 基因注释（位置/链/名称）
    └── web_subgraph.json # Top 节点子图（节点+边）
```

### 3.3 场景注册表形态

```js
// core.js
const SCENES = {
  movie:  { name:'🎬 电影排序', accent:'#38bdf8', panels:[kpiPanel, posterBoardPanel, ...] },
  amazon: { name:'📦 电商商品', accent:'#fb923c', panels:[...] },
  bike:   { name:'🚲 城市骑行', accent:'#34d399', panels:[...] },
  web:    { name:'🌐 网页图',   accent:'#818cf8', panels:[...] },
  flight: { name:'✈️ 航班准点', accent:'#f472b6', panels:[...] },
  gene:   { name:'🧬 基因组',   accent:'#22d3ee', panels:[...] },
};
```

每个 panel 是 `{ id, title, note, need:[files], mount(el, ctx) }`。
`ctx` 提供 `scn`、`meta`、`fetchJSON()`、`loadMap()`、`charts` 等公共能力。

### 3.4 通用组件（六场景复用）

| 组件 | 说明 | 替换现有 |
|---|---|---|
| `cardBoard` | 榜单表 + 排名徽章 + 迷你条 + 数值列 | `#g-tbl` / `#tbl-topk` |
| `rankMove` | **双榜名次迁移图**（slope/bump） | 新增，A/B 场景共用 |
| `searchCard` | 检索卡片（支持封面图 + 多字段） | `#g-seout` / `#se-out` |
| `histBar` | 分布直方图（对数轴可选） | 新增，B/D/E 共用 |
| `geoMap` | 地图封装（注册 GeoJSON + 散点/流线 + 缩放） | 新增，C/E 共用 |
| `keyLab` | **键位实验台**（拖动子键优先级 → 榜单实时变化，并显示 int64 键） | 新增，核心教学组件 |
| `timeline` | 时间轴趋势（支持"缺月标注"） | `#g-ch-year` |

> `keyLab` 是本方案的"算法叙事核心"：题目考察的是"多级键编码 → 单 int64 键 → 排序"。
> 让学生**拖动"航班量 / 平均延误 / 机场"的优先级顺序**，榜单实时重排，
> 并同步显示 `key = origin<<25 | minute<<4 | delayIdx` 的二进制拼装过程——
> 这比任何条形图都更能说明"排序是这些系统的关键子问题"。

## 四、数据增强管线（enrichment）

新增一个**独立的、可重复运行的**脚本目录，把"原始数据 → 领域资产/增强 JSON"，
不污染现有 `pre_<scn>.py` 的数据契约（`postings.dat`/`entities.dat` 保持不动）。

```
app/pre/
├── enrich_common.py      # 共用：HTTP（含代理）、缓存、断点续传、限速重试
├── enrich_movie.py       # links.csv + 海报下载 + 评分直方图 + 多类型
├── enrich_amazon.py      # meta_Electronics.json.gz → 标题/价格/图片/类目树
├── enrich_bike.py        # 年度 zip 流式扫描 lat/lon + OD 聚合 + 时刻矩阵
├── enrich_flight.py      # OpenFlights 坐标 + 航司名 + 航线/准点率聚合
├── enrich_gene.py        # NCBI GFF → 基因注释
└── enrich_geo.py         # GeoJSON 底图抓取与坐标简化
```

**运行方式**：`python app/pre/enrich_all.py [--proxy http://127.0.0.1:7890] [--scope topk|all]`

### 4.2 关键实现要点（踩坑记录）

1. **Amazon meta 不是 JSON**：文件每行是 **Python repr（单引号）**，`json.loads` 会失败，
   必须用 `ast.literal_eval`。实测报错：`Expecting property name enclosed in double quotes: line 1 column 2`。
2. **不要用 OurAirports 那份 CSV**：实测 `davidmegginson.github.io/ourairports-data/airports.csv`
   只解析出 711 个 IATA 码，对本项目机场覆盖 **0/356**。用 OpenFlights `airports.dat`（99.4%）。
   *（该文件本身可用，但需以官方完整版为准并二次校验覆盖率。）*
3. **Citi Bike 月度直链已失效**：`201901-citibike-tripdata.csv.zip`、`201901-citibike-tripdata.zip`
   均返回 **404**；只有年度包 `2019-citibike-tripdata.zip`（858.7MB）可用。

6. **媒体文件本地化**：海报/商品图应下载到 `assets/` 并在清单里记录本地文件名，
   保证**离线演示可用**；下载失败的条目在清单里标记 `null`，前端渲染占位图。

| `GET /api/web/subgraph?nodes=800` | 邻接子矩阵 / 枢纽子图 | D |

但它是 A/B 场景最有说服力的可视化，**优先实现**。

### 11.3 接口层与数据层解耦

`ed::EntityStore` 目前只按 `postings.dat`+`entities.dat`+`meta.txt` 装载。
增强数据（坐标、图片、聚合）应走**独立的小 JSON 文件按需读取**，
不要塞进 `EntityStore`——保持"新增场景只需 ①预处理脚本 ②meta.txt"的既有扩展卖点。

## 十三、风险与降级策略

| 风险 | 影响 | 降级策略 |
|---|---|---|
| 演示环境无外网/无代理 | 海报、商品图、GeoJSON 全部加载失败 | **资产必须本地化**（`assets/`），并在 `maps.meta.json` 标记缺失项；前端统一占位图 |

| Amazon meta 与 ratings 的 ASIN 不完全交集 | 部分商品无标题/价格 | UI 显示覆盖率；卡片缺失字段显示"—"而非 0 |

| 地图 GeoJSON 体积（纽约 3MB） | 首屏加载慢 | 坐标简化（Douglas-Peucker，容差 ~0.0005）后预计 <600KB；或按需加载 |
| `calendar`+`heatmap` 组合未完成自动化验证 | 可能渲染异常 | 退化为日期序列柱状图（叙事不受影响） |
| 单线程 HTTP 服务器 + 多图请求 | 海报墙加载慢 | ① keep-alive ② Top-20 内联 base64 ③ 减少一次性展示数量（分页） |
| 骑行站点坐标跨月漂移 | 地图落点争议 | 取首次出现值，`stats.txt` 记录不一致站点数并如实披露 |

| 基因 `total_ms` 缺失 | "排序占比 90%" 无法自证 | 补测写入 `total_ms`；未补测前 UI 只展示"排序合计 1.70s"，不写百分比 |

## 二十、深圳地图"边界与网格脱离"根因修复（2026-10-03）

用户截图指出：深圳地图的行政边界与网格点相互脱开（北京正常）。三层根因，逐层排除：

1. **坐标系标注错误（主因）**：平台官方标注坐标为 BD09，按标注做 BD09→GCJ02
   转换后整片点云偏西南约 4km（区界落入率仅 91.0%）。对齐检验（网格点落入
   区界率 × 多偏移量扫描）证实**实际坐标系是 WGS84**：按 WGS84→GCJ02 纠偏
   后零偏移落入率即达最优。`pre_bike_sz.py` 已改用 WGS84→GCJ02 标准算法，
   stats.txt 记录检验结论；北京数据本就与 GCJ02 底图对齐（未做转换），故无此问题。
2. **区外漂移点**：起/终点越出区界的 GPS 漂移单让点云漫过边界。改为
   **1.5km 缓冲带裁剪**——缓冲带内保留福田/皇岗/文锦渡/莲塘等口岸跨界簇
   （真实且有趣：文锦渡侧单格 3.3 万次），带外剔除 2,289 单（0.02%），stats 如实记录。
   性能注意：区界判定必须放在**唯一网格质心**上（每行做射线法会慢 3 个量级）。
3. **视野含空白远郊**（上一轮已修）：底图裁剪 + `boundingCoords` 自动适配。

验证：网格渲染图（`_map_check.png`）上网格与区界严丝合缝；ECharts 场景内
热点准确落在南山/宝安/福田/罗湖；重新生成后基准 10,602,597 键。
另修复：`mkChart` 暂存队列在后台标签页改用 `setTimeout` 轮询（rAF 在后台
不触发导致图表不渲染）、`scnSwitch` 补充队列 flush。
