# 多场景真实数据应用方案 —— 六领域验证"排序是许多领域的关键子问题"

> 目标：在已有 MovieLens（A）基础上新增 5 个真实数据场景（B~F）。
> 题目问题描述原文列举了"数据压缩、计算机图形学、计算生物学、供应链管理、
> 组合优化和投票"等领域——本方案覆盖 电商/供应链、城市出行/物流、搜索引擎、
> 航空调度、计算生物学/数据压缩 五个方向，报告可直接以
> **"一套排序框架 × 六个看似无关的真实领域"** 收束"排序是关键子问题"的论证。
>
> 核心认知（已验证）：框架是"数据集→预处理→排序矩阵→UI"的可插拔结构，
> 新增场景只需 ①一个预处理脚本 ②键打包设计 ③UI面板配置，排序内核
> （common/ + sortgen.h + AdaptSort）零改动。

## 一、统一框架（先做，半天）

### 1.1 数据契约（每个场景的预处理脚本输出同一组文件）

```
app/data/<scn>/
├── postings.dat     uint64 小端键序列 —— 该场景的"大排序负载"
├── entities.dat     TSV：id \t year \t category \t val(数值属性) \t name
├── meta.txt         场景元数据：键打包说明 / KPI 标签 / 直方图字段 / 榜单模式
└── stats.txt        数据体检摘要
```

`entities.dat` 用通用五段式（year/val 字段按场景复用：Amazon=价格、
Bike=平均时长、Web=PageRank×10⁹、Flight=平均延误、Gene=A/C/G/T组成），
避免每个场景一套数据结构。

### 1.2 代码改动清单

## 二、各场景详细设计

### B 电商商品 —— Amazon 评论（SNAP 版）【叙事：供应链管理/商品排序】

**数据收集**
- 主文件（CSV，免注册直链，已探测 200）：
  `https://snap.stanford.edu/data/amazon/productGraph/categoryFiles/ratings_Electronics.csv`
  约 500MB 文本，782 万条评分，四列 `userId,itemId,rating,timestamp`（与 MovieLens
  ratings 同构——预处理脚本几乎复制）。
- 扩展（可选，二选一）：`ratings_Books.csv`（5,100 万条）拉满规模；
  `meta_Electronics.json.gz` 提供商品名/价格/类目，用于价格分桶与名称检索。
- ASIN 字符串 id → 预处理期用 dict 压成稠密 int id（Bloom 换 dict，千万级内存 ~1.5GB 可控）。

**键打包**：`key = itemId << 26 | userLocal << 4 | ratingIdx`
（Electronics：商品 6.3 万 <2¹⁶，用户 169 万 <2²¹，评分 10 档 4 位；共 41 位）。

**排序任务与算法优势**
1. 商品关注度榜单（评论数↓→均分↓）——多级键编码，与 A 同源；
2. **类目倒排索引**：类目→商品 posting（类目 k≈500 → 计数排序 3 趟，对比快排 6~8×）；
3. **价格区间分桶**：val 字段按十Decile 分桶（桶排序的现实用例）；
4. 窄评分域：ratingIdx 计数排序 vs 比较类 25× 级差距（复用 A 的结论，换领域重现）。

**UI 面板**：KPI（商品数/评论数/用户数/价格中位数）、商品检索（名称子串）、
关注度和好评度双模式榜单、价格分布直方图、类目饼图。

**风险**：ratings CSV 简单格式风险低；meta JSON 可选不影响主线。磁盘峰值 +1.5GB。

### C 城市出行 —— Citi Bike 骑行日志【叙事：城市调度/物流】

**数据收集**
- S3 直链免注册（已探测 200）：`https://s3.amazonaws.com/tripdata/201901-citibike-tripdata.csv.zip`
  … 12 个月 2019（每月约 1.2~2 百万次骑行，zip 约 100~150MB），合计约 **1,700 万次骑行**。
- 2019 全年 schema 统一（tripduration, starttime, start station id/name, …），
  Python csv 流式解析。并行 8 线程下载约 10 分钟。
- 可扩展到 24 个月 ≈ 3,400 万（与 MovieLens 同量级）。

**键打包（两个键文件，两个真实任务）**
1. `postings.dat`：站点台账键 `key = stationId << 21 | minuteOfYear`
   （站点 ≈1,200 <2¹¹；年内心分钟 <2²¹）——文件自然时间序导出。
2. `ledger.dat`：**站点台账序** = 按站点聚合、站内按时间升序的拼接序列
   （这是真实系统里的产物——"每站一份按时间的骑行台账"）。
   对台账键追加新月份导致的尾部乱序 = **真实版"块状近序"**——
   正是 CVE替身构造的现实原型，AdaptSort 的 S7 run 归并路径直接兑现
   （inv_rate 低 + asc_prefix 高 → 归并只搬尾部）。

**算法优势**
1. **k≈1,200 的计数排序**：1,700 万键 3 趟线性扫描 ≈0.2s vs 快排 ≈2s，**8~10×**；
2. **稳定性的现实意义**：台账按站点重排时，稳定排序自动保持站内时间序
   （计数/归并），不稳定排序（快排/堆）必须键编码 (station,time)——两条路径定量对比；
3. 增量维护场景的近序块结构 → AdaptSort 决策可追溯（trace 显示 asc_prefix≈0.9）。

**UI 面板**：KPI（骑行量/站点数/自行车数/平均时长）、热门站点榜（使用量↓）、
站点检索、24 小时骑行分布直方图、月度趋势线、**近序演示卡**（台账序 vs 乱序的
AdaptSort 决策对比，读 matrix 的 strategy 列）。

**风险**：无。2019 schema 一致、直链稳定。磁盘峰值 +5GB（解压后 CSV）。

### D 搜索排序 —— Stanford Web 图 + PageRank【叙事：搜索结果按重要性排序】

**数据收集**
- `https://snap.stanford.edu/data/web-Google.txt.gz`（1.5MB gz！已探测 200）
  875,713 节点 / 5,105,039 边，文本边表 `FromNodeId\tToNodeId`。

**实现（C++，~150 行）**
1. **CSR 构建**：边表 510 万条按 `src<<20|dst` 编码排序后分段——图加载的
   真实瓶颈就是这次大排序（矩阵第一负载）；
2. **PageRank 幂迭代**：damping=0.85，迭代 20 轮（或 ||Δ||<10⁻⁶）；
3. **IEEE-754 保序映射**（req7 预留改进⑧的应用层落地，~10 行）：
   `u64 = bits(d); u64 = (i64)u64 < 0 ? ~u64 : u64 ^ (1ull<<63);`
   ——把 double 分值转成 int64 后**直接复用全部 8+1 算法与 AdaptSort**；
4. 每轮迭代后堆选择 Top-K（检索层）。

**矩阵负载**：边键 510 万（建图）+ 分值键 87.5 万（排名，浮点映射后）。

**算法优势**
1. 浮点键→int64 的保序映射是**本场景独有**的教学点：不做映射任何整数排序算法
   都无法正确处理 double；
2. 图加载的排序瓶颈论证（510 万边排序 vs PageRank 迭代本身的计时分解）；
3. 迭代内 Top-K：堆选择在 20 轮迭代中反复调用——O(n log k) 的现实意义。

**UI 面板**：KPI（节点/边/迭代轮数/收敛残差）、Top-100 网页榜单
（如实显示 `Node #id`——web-Google 无节点名，诚实标注）、PageRank 收敛曲线、
入度分布（长尾，log 轴）、分值分布直方图。

**风险**：排序在总计算中占比有限 → 报告用"CSR 构建 + 每轮 Top-K + 最终排名"
三处排序职责补强叙事。无节点名是数据本身属性，UI 如实呈现即可。

### E 航空准点 —— 美国DOT航班数据【叙事：调度/长尾分布】

**数据收集**
- 直链模式（已探测 200）：
  `https://transtats.bts.gov/PREZIP/On_Time_Reporting_Carrier_On_Time_Performance_1987_present_2019_{M}.zip`
  12 个月 2019，每月 zip 60~70MB，全年约 800MB；每月 55~70 万航班，合计约 **750 万行**。
- CSV 宽表约 110 列——Python `csv` 流式只取 8 列
  (FlightDate, Carrier, Origin, Dest, DepTime, DepDelay, ArrDelay, Distance)，
  其余丢弃（磁盘友好）。

**键打包**
1. `postings.dat`：机场台账键 `key = originId << 22 | depMinuteOfYear`
   （机场 ≈350 <2⁹；分钟 <2²¹）——文件自然序（按日期）导出；
2. `ledger.dat`：航司台账序（承运人分块、块内时间升序）——块状近序第二例。

**算法优势**
1. **长尾分布的计数分桶**：延误值域 [-60, 2000+] 分钟，尾部截断到 k≈2,600 桶后
   计数排序可行——750 万键 3 趟 vs 快排，**5~8×**；长尾在直方图上一眼可见；
2. 多级键延误榜（延误↓→航司→日期）；
3. 航司台账块状近序 → AdaptSort merge 路径（同 C 的增量叙事，换领域重现）。

**UI 面板**：KPI（航班量/机场数/航司数/平均延误）、机场倒排检索、
延误 Top 榜（可按航司过滤）、延误长尾直方图、月度准点率折线。

**风险**：PREZIP 直链模式偶尔变化 → 备选把月份减到 4 个月（仍有 250 万行），
或改用 2019 年以前的小文件。解析时注意 DepDelay 含 NaN（取消航班）——跳过。

### F 计算生物学/数据压缩 —— 基因组后缀数组【叙事：数据压缩/计算生物学，题目点名领域】

**关键设计决策（消除风险）**：后缀数组**倍增法**的每一轮排序对象是
`(rank[i], rank[i+k])` 的**整数对**——编码为 `key = rank1 << 32 | rank2` 后
就是纯 int64 键，**完全复用现有 8+1 算法，无需任何字符串比较器**。
原方案"F 工程量完全不是一个量级"的风险评估是基于朴素字符串排序；
用倍增+整数编码后，本场景与 B/C/E 同量级可做。

**数据收集**
- NCBI RefSeq 直链（已探测 200）：
  `https://ftp.ncbi.nlm.nih.gov/genomes/refseq/bacteria/Escherichia_coli/reference/GCF_000005845.2/GCF_000005845.2_ASM985v2_genomic.fna.gz`
  （1.4MB gz，E. coli K-12 基因组 4.64 Mb）——起规模刚好；
  扩展档：人类 chr22 FASTA（~50Mb，直链同样模式），仍在 int64 键能力内
  （rank < 2³² 各占 32 位）。

**实现（C++，~180 行）**
1. FASTA 解析（去头行、换行；A/C/G/T→0..3，分隔符 $）；
2. 初始 rank 按 2-mer 计数排序一次得到；此后每轮：
   `key = rank[i] << 32 | rank[i+k]` → 排序（**矩阵负载：4.64M 键 × 23 轮**）→
   重编 rank，k 翻倍至 ≥n；
3. BWT：`bwt[i] = T[SA[i]-1]`；MTF+RLE+Huffman 任选一做压缩率测量；
4. 后缀数组二分搜索：O(m log n) 子串出现位置查询——UI 交互演示点。

**算法优势（六个场景中"排序=瓶颈"论证最强的）**
1. 每一轮都是**全量大排序**，n log n 轮中排序占后缀数组构造时间的 ~90%——
   换排序算法直接乘到总耗时上（radix vs shell 的差距 × 23 轮）；
2. (rank[i], rank[i+k]) 复合键 = 多级键编码的又一真实用例；
3. 每轮的键域是"上一轮的 rank"——键域随轮次收缩，**计数排序在后期轮次
   k=n 逐渐最优**的动态过程可观测（trace 每轮的决策变化）。

**UI 面板**：KPI（序列长度/碱基组成）、碱基组成饼图、每轮排序耗时×算法折线
（23 轮）、BWT 压缩率卡、**子串搜索演示**（输入 "ACGT" 片段 → 后缀数组二分
→ 出现位置列表 + 耗时）。

**风险**：倍增轮内排序调用现有算法，逻辑简单；唯一要小心的是 rank 重编号的
正确性——用"排序后逐对比较相邻 key 是否相等"重编 rank（教科书标准做法），
加一个小规模对拍测试（暴力排序后缀的前 1000 个后缀）兜底。

## 四、报告整合：六场景 × 题目领域映射
